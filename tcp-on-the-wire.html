Transmission Control Protocol

TCP on the WireEvery field, every state, every packet — from the first SYN to the last ACK, animated.

TCP takes an unreliable, out-of-order, duplicating, packet-dropping network and hands your application a clean, ordered, reliable stream of bytes. This page shows exactly how — by drawing the packets.

Where TCP sits

Four layers, four headers, one bundle of bytes

Your note said “the application layer does not know about bottom layers — it is just an order to pass data.” That’s the right instinct. Here’s the mechanism behind it.

When your code calls send(sock, buf, 1460), it hands 1,460 bytes to the kernel and gets an integer back. It never sees a port number, a sequence number, or a MAC address. Each layer below it prepends its own header and passes the whole thing down — a process called encapsulation. On the receiving machine the same layers strip their headers back off, in reverse.

Worth refining

The application is insulated from TCP’s mechanics — but it is not fully blind to them. It feels TCP through the socket API: send() blocks (or returns a short count) when the send buffer fills because the receiver’s window closed; TCP_NODELAY switches off Nagle’s algorithm; SO_RCVBUF caps the window TCP can advertise. The abstraction leaks in exactly the places where performance lives.

The idea everything else hangs on

TCP is a stream of bytes, not a stream of messages

If you take one thing from this page, take this. It explains sequence numbers, it explains why your API keeps breaking, and it is the single most common blind spot in TCP notes.

TCP does not transport your messages. It transports a numbered stream of bytes. Every byte in the connection, in each direction, has its own 32-bit number. A segment is just a claim: “here are bytes 4381 through 5840”.

The consequence is blunt: TCP does not preserve the boundaries of your send() calls. The kernel is free to merge several sends into one segment, or split one send across many. The receiver’s recv() returns whatever bytes have arrived — never a guarantee of “one message.”

What a sequence number actually counts

Because the unit is the byte, the sequence number field holds the number of the first data byte in this segment — not a packet counter. That single fact makes every trace readable:

The rule

next_seq = seq + len(payload)   (+1 if SYN or FIN is set)

and, on the other side: ack = the next byte I expect — meaning “I have every byte below this one.”

SYN and FIN carry no data but each consumes one sequence number — a “phantom byte.” That is why the handshake acknowledges ISN + 1. Your notes had the +1 right; this is the reason for it. It also means SYN and FIN are themselves retransmitted reliably, like data.

With a 32-bit field the numbers wrap after 4 GiB. On a 100 Gbit/s link that is under half a second, which is one of the reasons the Timestamps option (RFC 7323) exists — its PAWS mechanism rejects segments from a previous wrap of the sequence space.

Reading a trace

Wireshark shows relative sequence numbers by default: it subtracts each side’s ISN so the SYN reads seq=0. The real number on the wire is a large random value. Toggle it under Preferences → Protocols → TCP → Relative sequence numbers. Every number on this page is shown both ways.

Correction to your notes

You wrote Data offset (4) | reserved (3) | Flag | Window (16). The current spec is Data Offset (4) · Reserved (4) · Control Bits (8) · Window (16).

The 3-bit reserved field you noted is a real layout, just an obsolete one. The history: RFC 793 had 6 reserved bits and 6 flags. RFC 3168 (ECN, 2001) took two of them for ECE and CWR, leaving 4 reserved. RFC 3540 (2003) took a third for the NS nonce-sum bit, leaving 3 — that’s the version in most textbooks and diagrams. But RFC 8311 (2018) reclassified NS as historic, so the field is back to 4 reserved bits and 8 control bits. All four reserved bits must be sent as zero.

Correction to your notes

You wrote 16 bit = 65535. 16 bits encodes 65,536 distinct values — 0 through 65,535. The 65,535 figure is the largest value, not the count. For ports it works out close to your number anyway, because port 0 is reserved and never used on the wire, leaving 65,535 usable ports.

Your reasoning on Data Offset was exactly right, so it’s worth spelling out the arithmetic: the field counts 32-bit words, not bytes. The minimum legal value is 5 (5 × 4 = 20 bytes, a header with no options) and the maximum a 4-bit field can hold is 15 (15 × 4 = 60 bytes). That 40-byte ceiling on options is a real constraint — it is why TCP extensions fight over space and why a modern SYN carrying MSS, SACK-permitted, Timestamps and Window Scale is already using 20 of the 40 bytes available.

PSH is not what most people think

PSH does not mean “important” or “send faster.” It is a delivery hint to the receiving kernel: stop buffering, wake the blocked recv(). On modern stacks the sender sets it automatically when its send buffer empties, so in a trace you will see PSH on the last segment of each response body. You cannot control it portably from the socket API.

The four-tuple: what “a connection” really is

A TCP connection is not identified by a port. It is identified by four values together:

( source IP , source port )  ⟷  ( destination IP , destination port )

Change any one of the four and it is a different connection with its own sequence space, its own window, and its own state machine. This is why a thousand browsers can all talk to 203.0.113.42:443 at once, and why one browser can open six connections to the same server:

Ephemeral ports — refining your note

Correction to your notes

You wrote that Chrome or a mobile app “does not use a port” until it makes a request. More precisely: a client does not listen on a port — it has no bind() + listen() socket waiting for inbound connections. But the moment it opens a connection, the kernel must assign it a local source port, because the four-tuple needs one. It picks an unused one from the ephemeral range. So the port is allocated per connection, not per application, and it is released back to the pool when the connection finishes its TIME_WAIT.

The IANA dynamic range is 49152–65535, exactly as you noted. Real operating systems mostly ignore it:

Why this matters in production

A busy proxy or API gateway opening connections to one upstream IP:port can only vary the source port — so it caps out at roughly 28,000 concurrent connections on Linux, minus everything stuck in TIME_WAIT for 60 seconds. That is the real cause of the classic EADDRNOTAVAIL / Cannot assign requested address error under load. The fixes are connection pooling and keep-alive (fewer connections), widening ip_local_port_range, or adding upstream IPs.

Opening a connection

Why the handshake needs exactly three messages

Your handshake diagram was correct. Here is what each of the three segments is actually for, and the one number in your worked example that was swapped.

The handshake is not a greeting. It exists to solve one specific problem: both sides must agree on where their byte stream starts, and each must confirm that the other heard it. That takes three messages, not two, and not four.

  1. SYN — the client proposes its Initial Sequence Number (ISN). Client’s number sent, unconfirmed.
  2. SYN + ACK — the server acknowledges the client’s ISN and proposes its own, in one segment. Client’s number confirmed; server’s number sent, unconfirmed.
  3. ACK — the client confirms the server’s ISN. Both confirmed. Connection established.

Two messages would leave the server’s ISN unconfirmed. Four would be redundant, because step 2 piggybacks two jobs onto one segment. Three is the minimum — this is a general result for reliable connection setup, not a TCP quirk.

Correction to your notes

Your worked example had the client using ephemeral port 50123 and the server on 3000. The SYN+ACK line was right (S-3000 → D-50123), but the final ACK repeated it. The third segment is sent by the client, so the ports flip back:

1. SYN       src 50123 → dst 3000    seq=1000  ack=—
2. SYN, ACK  src 3000  → dst 50123   seq=2000  ack=1001
3. ACK       src 50123 → dst 3000    seq=1001  ack=2001   ← ports flip back

Your sequence and acknowledgment numbers were exactly right. Source and destination ports always swap with direction — that is how the receiving kernel finds the right socket in its connection table.

The ISN is not really random

You wrote that the sender “selects a Sequence number randomly within 32 bits.” Close, and the intent is right — but a purely random ISN turned out to be a security hole. If an attacker can guess your ISN, they can inject forged segments into your connection without ever seeing it (the 1994 Mitnick attack).

RFC 6528 specifies what stacks actually do:

ISN = M + F( localIP, localPort, remoteIP, remotePort, secretKey )

  M = a 4-microsecond timer  — always moving forward
  F = a cryptographic hash   — unguessable, but stable per four-tuple

The timer component keeps ISNs increasing over time so that an old, delayed segment from a previous connection on the same four-tuple can’t be mistaken for a new one. The hash component makes it unguessable from outside. So: unpredictable, yes; random, not quite.

What the server is really doing: two queues

“The server accepts the connection” hides a detail that matters when things go wrong. The kernel keeps two queues per listening socket:

SYN cookies

When the SYN queue overflows, Linux can stop allocating memory per half-open connection entirely. It encodes the connection state into the ISN it sends back — a hash of the four-tuple plus a coarse timestamp and an MSS index. If the client’s final ACK comes back with ack = cookie + 1, the server recomputes the hash, confirms it, and builds the connection state on the spot. A flood of forged SYNs then costs the server no memory at all. The tradeoff: options negotiated in the original SYN (window scale, SACK, timestamps) mostly can’t be recovered, so cookie-built connections perform worse. It is an emergency valve, not a default: net.ipv4.tcp_syncookies = 1.

Skipping the wait: TCP Fast Open

RFC 7413 lets a client carry data in the SYN itself. On a first visit the server hands out a cookie; on later visits the client sends SYN + cookie + the HTTP request together, and the server can start replying before the handshake finishes — saving a full round trip. Support is patchy because middleboxes drop SYNs carrying unfamiliar options, and QUIC’s 0-RTT largely replaced the idea.

Moving data

The sliding window, and who is allowed to send what

Your note — “the source can send that amount of data without ACK” — is the right mental model for flow control. It’s half of the real answer.

Without a window, TCP would be stop-and-wait: send a segment, wait for its ACK, send the next. On a link with 50 ms of round-trip delay that caps you at about 1,460 bytes per 50 ms — roughly 230 kbit/s, no matter how fast the wire is.

The window fixes this. The receiver advertises how many bytes it can absorb, and the sender may have that many in flight, unacknowledged, at once. As ACKs come back the window slides forward and more can go out.

Sender’s send window

Advertised window 10 KB
1 · sent & ACKed 2 · sent, in flight 3 · usable window — may send now 4 · outside the window — must wait
SND.UNA 0 SND.NXT 0 in flight 0 KB usable 0 KB
Regions 2 + 3 together are the advertised window. Its left edge moves when an ACK arrives; its right edge moves when the receiver advertises more room.
Correction to your notes

You wrote “the destination port will say the window size.” The window is not a property of a port or of one side. Every segment carries the sender’s own receive window — so the client tells the server how much the client can accept, and the server tells the client how much the server can accept, continuously, in both directions, on every single segment including pure ACKs.

The bigger correction

The receiver’s window is only one of two limits. The real amount a sender may have outstanding is:

in flight  ≤  min( rwnd , cwnd )

 rwnd — receive window: "how much can you buffer?"  → flow control, set by the receiver
 cwnd — congestion window: "how much can the network carry?" → congestion control, guessed by the sender

cwnd is never transmitted. There is no field for it in the header — it is a private variable each sender maintains, adjusted by inference from ACKs and losses. Almost every real transfer is limited by cwnd, not by the advertised window. That’s the next section.

65,535 bytes was not enough

The window field is 16 bits, so the largest window it can express is 65,535 bytes. Consider a 1 Gbit/s link with a 100 ms round trip. The bandwidth-delay product — the amount of data that must be in flight to keep the pipe full — is:

1,000,000,000 bit/s × 0.1 s ÷ 8  =  12,500,000 bytes  ≈ 12.5 MB

A 64 KB window would use about 0.5% of that link. The fix is the Window Scale option (RFC 7323): each side sends a shift count S in its SYN, and from then on every window field is multiplied by 2S. With the maximum S = 14 the window reaches 1 GiB.

Two gotchas that bite in practice

The SYN’s own window field is never scaled — scaling only applies to segments after the handshake, because the option hasn’t been agreed yet when the SYN is sent. And scaling is only enabled if both sides offer it; if a middlebox strips the option from one SYN, the connection silently falls back to 64 KB windows and a fast link mysteriously runs at a few Mbit/s. This is why the raw field and the scaled value are shown separately in the Lab inspector above.

When the window hits zero

If the receiving application stops calling recv(), the kernel’s receive buffer fills and it advertises win=0. The sender must stop — and now there’s a deadlock risk, because the segment that re-opens the window is an ACK, and ACKs are not retransmitted. If it is lost, both sides wait forever.

TCP breaks this with the persist timer. The sender periodically transmits a window probe: a one-byte segment sent deliberately outside the window, purely to force the receiver to reply with a current window advertisement. Try it above with “Stall the receiver.”

The related pathology is silly window syndrome: a receiver that frees 1 byte and immediately advertises win=1 invites a 1-byte segment carrying 40 bytes of header. Both ends defend against it — receivers withhold small window updates until a meaningful amount of space is free (David Clark’s rule), and senders refuse to send tiny segments (Nagle’s algorithm).

Nagle and delayed ACK: the classic 40 ms stall

Two optimisations that are individually sensible and together pathological — this is the single most common cause of “my API is mysteriously slow by exactly 40 milliseconds.”

Nagle’s algorithm sender

“Don’t send a small segment while I have unacknowledged data outstanding — coalesce it with what comes next.” Stops a telnet session from sending a 41-byte packet per keystroke. On by default; disable with TCP_NODELAY.

Delayed ACK receiver

“Don’t ACK immediately — wait up to 40–200 ms in case I get a second segment to acknowledge, or some data to piggyback the ACK onto.” Halves the number of pure-ACK packets. On by default; Linux has TCP_QUICKACK, which is not sticky.

Now put them together. Your client writes a request in two send() calls — headers, then body:

client → sends chunk 1 immediately        (nothing outstanding, so Nagle allows it)
client → chunk 2 is small and chunk 1 is unACKed  → Nagle holds it back
server → has only one segment, no data to piggyback  → delayed ACK holds the ACK
       ⋯ 40 ms of nothing ⋯
server → delayed-ACK timer fires, sends the ACK
client → Nagle releases chunk 2

The fix is almost never TCP_NODELAY alone — it is writing the whole message in one send() (or one writev()). Nagle only holds back small writes that follow unacknowledged data; a single full write never trips it. Set TCP_NODELAY as well for interactive and RPC workloads, where latency beats packet efficiency.

The PMTU black hole

If a router along the path has a smaller MTU than your segment and the packet has DF (don’t fragment) set, the router is supposed to drop it and reply with ICMP Type 3 Code 4, “fragmentation needed,” carrying the correct MTU. Path MTU Discovery relies on this. When a firewall blocks all ICMP — an extremely common misconfiguration — the sender never hears anything. The handshake succeeds (small packets), then the first full-size data segment vanishes silently and the connection hangs. Symptom to recognise: small requests work, large ones stall forever. Linux mitigates this with net.ipv4.tcp_mtu_probing = 1.

Reliability & congestion

How TCP notices a packet vanished — and what it does next

Nothing on the network tells the sender a packet was dropped. No router sends a complaint. TCP has to infer loss, and its entire performance character comes from how it does that.

There are exactly two signals, and they mean very different things.

1 · The retransmission timer expires

The sender started a clock when it sent the segment. The clock ran out with no ACK. This is the slow, pessimistic signal: TCP assumes the network is badly congested, collapses cwnd to 1 segment, and restarts slow start. It also doubles the timer for the next attempt — exponential backoff.

2 · Three duplicate ACKs arrive

Later segments did get through, so the receiver keeps re-acknowledging the same byte — the hole. Since data is still flowing, the path clearly works. This is the fast, optimistic signal: retransmit immediately without waiting for the timer, and halve cwnd rather than collapsing it. This is fast retransmit, and it is what happens in the Lab trace above.

Why three duplicate ACKs?

Because the network reorders packets. If segments 3 and 4 simply arrive in the wrong order, the receiver emits one duplicate ACK and then everything is fine — retransmitting on the first duplicate would waste bandwidth constantly. Three duplicates is an empirical threshold: reordering that deep is rare, real loss that shallow is common. It is a heuristic, tuned by measurement, not a proof.

The retransmission timeout is a moving estimate

How long should the sender wait before declaring a segment lost? Too short and it floods the network with needless copies; too long and every loss costs seconds. TCP measures the round trip continuously and tracks both its average and its variance (RFC 6298, from Jacobson and Karels’ 1988 work):

on every RTT sample R:
  RTTVAR = 0.75 × RTTVAR + 0.25 × |SRTT − R|   how jittery is this path?
  SRTT   = 0.875 × SRTT   + 0.125 × R          smoothed round-trip time

  RTO    = SRTT + 4 × RTTVAR                   then clamped to ≥ 1 s

Including the variance term is the crucial part: a path with a steady 200 ms RTT gets a tight timeout, while a jittery mobile link with the same average gets a generous one. Before 1988, TCP used the average alone and the internet suffered repeated congestion collapse — senders timing out early, retransmitting, and making the congestion worse.

Karn’s algorithm

Never take an RTT sample from a retransmitted segment. When the ACK arrives you cannot tell whether it answers the original or the copy, so the sample would be garbage in either direction. TCP simply discards those samples — and relies on the Timestamps option, which stamps each segment so the ambiguity disappears entirely.

SACK: telling the sender exactly what’s missing

A plain ACK is purely cumulative — ack=2921 means “I have everything below 2921” and says nothing about what arrived after the hole. Without more information a sender that loses two segments in one window may end up retransmitting an entire window of data it already delivered successfully.

Selective Acknowledgment (RFC 2018) fixes this. Both sides advertise SACK-permitted in their SYN; afterwards the receiver can attach up to three or four blocks of already-received byte ranges as a TCP option:

ACK ack=2921  SACK=4381–8761

  "I'm missing 2921–4380. I already have 4381 through 8760 — don't resend those."

The sender retransmits precisely the hole. In the Lab trace above, watch the SACK block on the three duplicate ACKs grow as each later segment arrives — that is the receiver narrowing down the damage in real time.

Congestion control

The sawtooth

Flow control protects the receiver. Congestion control protects the network — and it is the part with no header field at all.

The four phases, in words

  1. Slow start — badly named; it is the fastest phase. cwnd starts at 10 segments (RFC 6928; it was 1 in the original design) and doubles every round trip — exponential growth, probing for the pipe’s capacity as quickly as it dares.
  2. Congestion avoidance — once cwnd passes ssthresh, growth switches to +1 segment per round trip. Linear, cautious: we are near capacity, so creep up.
  3. Fast retransmit & fast recovery — on three duplicate ACKs, resend the missing segment, set ssthresh = cwnd / 2, set cwnd = ssthresh, and continue in congestion avoidance. The connection survives the loss without stalling.
  4. Timeout — the expensive one. ssthresh = cwnd / 2, cwnd = 1, back to slow start. A single RTO can cost more throughput than dozens of fast retransmits.

Why loss-based control has a problem

Reno and CUBIC treat a dropped packet as the signal to back off. That works when router buffers are small. Modern routers ship with enormous buffers, so under load they don’t drop — they queue, adding hundreds of milliseconds of delay before any loss occurs. Loss-based TCP happily fills those buffers, and everything sharing the link becomes laggy. This is bufferbloat. It is why BBR measures delivery rate and minimum RTT instead of waiting for drops, and why ECN exists: routers mark packets with a congestion bit instead of discarding them, and the receiver echoes it back with the ECE flag — congestion signalled at zero cost.

Check and change what your machine uses:

$ sysctl net.ipv4.tcp_congestion_control
net.ipv4.tcp_congestion_control = cubic

$ sysctl net.ipv4.tcp_available_congestion_control
net.ipv4.tcp_available_congestion_control = reno cubic bbr

$ sudo sysctl -w net.ipv4.tcp_congestion_control=bbr   # per-host default
Shutting down

Four steps, sometimes three, and one state that lingers

Your four-step teardown was right. What’s missing is why it needs four when opening needs three, and what happens in the sixty seconds afterwards.

The asymmetry has a simple cause: a TCP connection is two independent one-way streams, and each is shut down separately. FIN does not mean “goodbye” — it means “I have no more data to send. You may keep sending.” That state is called a half-close, and it is a real, usable condition, not an error.

So each direction needs its own FIN and its own ACK: four segments. The handshake gets away with three only because the middle segment does double duty.

Very often it’s three, not four

If the closing side’s application also has nothing more to send — the common case — the receiving kernel can coalesce the ACK for the incoming FIN with its own outgoing FIN into a single FIN, ACK segment. In real traces a three-segment close is at least as common as a four-segment one. Both are correct.

TIME_WAIT: the state everyone tries to delete

After sending the final ACK, the side that closed first does not go straight to CLOSED. It sits in TIME_WAIT for 2 × MSL — twice the Maximum Segment Lifetime, the longest a segment is assumed to survive in the network. The RFC value of MSL is 2 minutes, so 4 minutes; Linux hardcodes 60 seconds.

It exists for two distinct reasons, and both are real:

  1. The final ACK might be lost. If it is, the peer’s LAST_ACK timer fires and it retransmits its FIN. Someone has to still be there to answer. A socket that vanished immediately would answer with a RST, and the peer would report a connection error on a perfectly clean shutdown.
  2. Old segments must expire. The four-tuple may be reused by a brand-new connection at any moment. If a delayed duplicate from the old connection were still wandering the network, it could arrive with a sequence number that happens to fall inside the new connection’s window and silently corrupt its stream. Waiting 2×MSL guarantees every straggler is gone.
Practical fallout

A machine making many short outbound connections accumulates thousands of TIME_WAIT entries, each holding an ephemeral port. Two options are usually offered; only one is safe.

net.ipv4.tcp_tw_reuse = 1 — reasonable. Lets a new outbound connection reuse a TIME_WAIT four-tuple when timestamps prove the old one is stale. Client-side only.

net.ipv4.tcp_tw_recycle — do not use. It broke connections from clients behind NAT and was removed from Linux entirely in kernel 4.12. Plenty of stale blog posts still recommend it.

The real fix is upstream: keep connections alive and pool them, so you aren’t opening and closing thousands of them in the first place. And have the client close first where possible, so TIME_WAIT accumulates on the machine with spare ports rather than on the server.

CLOSE_WAIT is always your bug

Worth knowing on sight, because it is unambiguous. A socket enters CLOSE_WAIT when the peer’s FIN arrives and the kernel ACKs it. Leaving that state requires your application to call close(). Nothing else will move it. There is no timeout.

So a pile of sockets stuck in CLOSE_WAIT means exactly one thing: your code is leaking file descriptors — reading until EOF and never closing, an exception path that skips cleanup, a connection pool that doesn’t reap. Unlike TIME_WAIT, it is never a tuning problem and never resolves on its own.

Keepalive: detecting a peer that simply disappeared

An idle TCP connection sends nothing. If the peer is powered off or its cable is pulled, no FIN and no RST is ever sent — your socket stays happily ESTABLISHED forever, pointing at a machine that no longer exists. This is a half-open connection (different from half-closed).

SO_KEEPALIVE sends a probe — a segment with a sequence number one behind the current one, which forces an ACK — after an idle period. Linux defaults are conservative to the point of uselessness for most services:

tcp_keepalive_time   = 7200   # 2 hours idle before the first probe
tcp_keepalive_intvl  = 75     # then every 75 s
tcp_keepalive_probes = 9      # give up after 9 → ~2h 11m to notice

Most application protocols implement their own heartbeat instead (HTTP/2 PING frames, WebSocket ping, gRPC keepalive), because they need detection in seconds and they need it to traverse proxies that would otherwise silently drop an idle connection.

Not drawn: simultaneous open, where both ends send a SYN at once and both go SYN-SENT → SYN-RECEIVED → ESTABLISHED. Legal, specified, and almost never seen outside NAT-traversal tricks.

The two vertical columns are the two ways a connection ends. Down the right: the side that calls close() first — FIN-WAIT-1 → FIN-WAIT-2 → TIME-WAIT. Which column your server lands in determines whether it accumulates TIME-WAIT sockets, which is why “who closes first” is an architectural decision, not a detail.

Integrity

The checksum, and the addresses hidden inside it

You had this right — “a mechanism so the destination can understand if the source sent wrong data, ones’ complement.” Two details make it more interesting than it looks.

The algorithm itself is deliberately cheap, because in 1981 it ran on hardware that could not afford a real hash:

  1. Set the checksum field to zero.
  2. Treat everything to be covered as a sequence of 16-bit big-endian words. Pad the data with a zero byte if its length is odd (the pad is not transmitted).
  3. Add them all with end-around carry — whenever the sum exceeds 16 bits, add the overflow back into the low bits. This is ones’-complement addition.
  4. Take the ones’ complement (bitwise NOT) of the result. That is the checksum.

The receiver sums the same words including the checksum field. A correct segment always sums to 0xFFFF, whose complement is 0x0000 — so the receiver just checks for zero.

Worked example

three 16-bit words
  0xE34F
+ 0x2396
─────────
  0x106E5      carry out of 16 bits …
  0x06E5 + 1 = 0x06E6   … added back in (end-around carry)

  0x06E6
+ 0x4427
─────────
  0x4B0D       final ones'-complement sum

  checksum = ~0x4B0D = 0xB4F2       what goes in the header

receiver:  0x4B0D + 0xB4F2 = 0xFFFF  →  ~0xFFFF = 0x0000  ✓ valid

What it covers — including twelve bytes that are never sent

Here is the part most notes leave out. The checksum is not computed over the TCP segment alone. It also covers a pseudo-header, assembled from IP-layer fields, which exists only in memory during the calculation:

Three consequences

NAT must rewrite it. A router that changes your source IP or port has invalidated the checksum, so it has to recompute — this is why NAT is a transport-layer operation, not a pure network-layer one, and why protocols that embed addresses in their payload (classic FTP, SIP) need special NAT helpers.

It is weak, and it is not your only protection. Sixteen bits catch roughly 1 error in 65,536, and the sum misses whole classes of reordering. It is a last-resort check on top of Ethernet’s 32-bit CRC. For data you truly care about, checksum at the application layer.

Your NIC probably computes it. Checksum offload means the kernel hands the card a segment with a placeholder. Which is why tcpdump on the sending host frequently shows cksum incorrect for outbound packets — you are seeing them before the hardware fills the field in. Nothing is broken.

One last contrast: in TCP the checksum is mandatory. In UDP over IPv4 it was optional (a zero field means “not computed”); over IPv6 it became mandatory there too, because IPv6 dropped its own header checksum.

TCP under HTTP

Does every API call cost a handshake?

Your answer to this was essentially correct. Here it is with the numbers attached, plus four refinements worth having.

No — not since 1997. A TCP handshake costs one full round trip before any application byte moves, and over HTTPS a TLS 1.3 handshake costs another. On a 60 ms path that is 120 ms of pure setup. Connection reuse is the single largest latency win available to an HTTP client, which is why every layer of the stack now does it by default.

Four refinements to your list

1 · HTTP/2 does not remove head-of-line blocking

It removes it at the HTTP layer — one slow response no longer blocks the others. But all those streams still ride one TCP connection, and TCP delivers bytes strictly in order. Lose one segment and the kernel holds back every stream’s data until the retransmission arrives, even streams whose bytes already made it. On a lossy link, HTTP/2 over TCP can be slower than HTTP/1.1 with six connections. Removing this is the entire reason HTTP/3 abandoned TCP: QUIC tracks loss per stream, so one lost packet stalls only its own stream.

2 · “Cross-origin” isn’t quite the trigger

Connection pools are keyed by (scheme, host, port) — and in modern browsers also by the top-level site, for privacy (network-state partitioning). Two different hostnames that resolve to the same IP still get separate pools. The exception is HTTP/2 connection coalescing: if two hostnames resolve to the same IP and the TLS certificate covers both, a browser may reuse one connection for both.

3 · Server-side limits also close connections

Your “connection pooling limits” point is right but usually server-driven. Nginx keepalive_requests (default 1000) and keepalive_timeout (75 s) will close the connection from the server side. AWS ALB idles out at 60 s by default — a classic source of intermittent 502s when the client’s idle timeout is longer than the load balancer’s and it reuses a connection the balancer has already closed. Always set your client’s idle timeout shorter than the server’s.

4 · The “fresh client per request” bug, by language

Your last point is the one that costs the most in real code, so here is what “share a persistent client” concretely means:

Go       one http.Client / http.Transport, package-level  — never per request
Python   requests.Session()  or  httpx.Client()             — not requests.get()
Node     an Agent with keepAlive:true, or undici's Pool     — fetch() defaults to keep-alive
Java     one OkHttpClient (it pools by default)             — or HttpClient, reused
.NET     IHttpClientFactory                                 — never `new HttpClient()` in a loop

The failure mode is distinctive: it works perfectly in development and exhausts ephemeral ports under production load, with EADDRNOTAVAIL and a huge TIME_WAIT count.

What to add next

Your notes covered the structure of TCP thoroughly. What they didn’t cover is its behaviour over time — congestion control, retransmission timers, and TIME_WAIT. That is where nearly every real-world TCP problem actually lives: a slow API is almost never a header-layout question and almost always an RTO, a closed window, or a connection that should have been reused.
