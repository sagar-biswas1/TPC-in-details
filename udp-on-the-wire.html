User Datagram Protocol

UDP on the WireEight bytes of header, no handshake, no memory, no promises — and most of the internet’s hardest-working traffic.

TCP spends a round trip asking permission and then guarantees delivery. UDP does neither. Understanding UDP is mostly understanding what it deliberately refuses to do for you — and what you therefore have to build yourself.

RFC 768 — the whole spec, 3 pages RFC 1122 — host requirements RFC 8085 — usage guidelines RFC 9000 — QUIC
What UDP actually is

A thin shim over IP that adds exactly two things

RFC 768 is three pages long. That is not a summary — that is the whole specification, published in 1980 and never revised.

IP can already get a packet from one host to another. What it cannot do is say which program on that host the packet is for, and it cannot tell you whether the payload arrived intact. UDP adds those two things and stops:

  1. Ports — 16 bits each way, so the kernel can demultiplex one machine’s inbound packets to the right socket.
  2. A checksum — optional over IPv4, mandatory over IPv6, covering the header, the payload and a pseudo-header of IP fields.

That is the complete feature list. Everything people find surprising about UDP follows from what is absent:

The reframe that makes UDP click

UDP is not “TCP with the safety off.” It is raw IP that you are allowed to address to a program. Think of it as the unopinionated floor of the transport layer: whatever guarantees your application needs, you build on top — and you build only the ones you need. That is why QUIC, the transport under HTTP/3, is built on UDP rather than on TCP. It was cheaper to rebuild reliability from nothing than to work around TCP’s decisions.

Anatomy

Four fields, eight bytes, and nothing else

TCP’s header has ten fields and a 40-byte options area. UDP’s has four fields and no options. There is nowhere to put a sequence number, an acknowledgment, a window, or a flag — which is precisely why it cannot offer reliability.

Source port 0 is legal here

Unlike TCP, UDP explicitly permits a source port of zero, meaning “no reply is expected — do not send one.” It is rare in practice (most stacks assign a real ephemeral port anyway, and many firewalls drop port-0 traffic as malformed), but it is in RFC 768 and it tells you something about the protocol’s mindset: a UDP send is not a request. It is an announcement.

The thing UDP does better

Message boundaries survive

Almost every comparison frames UDP as TCP minus features. This is the one place the direction reverses — and it is why some applications choose UDP even on a perfectly reliable network.

TCP is a byte stream: it may merge your writes or split them, and the receiver has no idea where one message ended and the next began. UDP is a datagram protocol: one send() produces exactly one datagram, and one recv() returns exactly one datagram, whole.

All or nothing

The boundary guarantee comes with a second, stronger one: a datagram is delivered whole or not at all. There is no such thing as receiving half a UDP datagram. If any IP fragment of it is lost, the whole datagram is discarded and your recvfrom() never sees it.

This is exactly the property DNS wants. A resolver that received 40 bytes of a 60-byte response would have to detect and discard it anyway. UDP does that for free — and if nothing arrives within the timeout, the resolver just asks again.

The gotcha this creates

Because a datagram is atomic, your receive buffer must be big enough for the whole thing. Call recvfrom() with a 512-byte buffer when a 900-byte datagram arrives and, on Linux, you get 512 bytes and the remaining 388 are discarded silently — the rest of the datagram is gone, not queued for the next read. Always size the buffer to your protocol’s maximum, or pass MSG_TRUNC so the return value tells you the true length and you can detect the truncation.

What that picture actually proves

TCP delivered 6 of 6 messages, perfectly ordered, and finished at t=40. UDP delivered 5 of 6, one of them out of order, and finished at t=18.

Neither result is “better.” They are answers to different questions. If the messages are database writes, TCP’s answer is the only acceptable one. If they are a player’s position in a game at 60 frames per second, message 3 was obsolete before TCP even noticed it was missing — and message 4 sat finished in the receiver’s buffer for sixteen time units waiting for a repair nobody wanted, with 5 and 6 queued behind it.

Look specifically at t=24 through t=40 on the TCP side. Message 4 arrived at the receiving machine at t=24. The bytes were in memory, intact, correct. The application could not have them, because TCP guarantees in-order delivery and byte 3 was missing. That is not a bug — it is the guarantee working exactly as designed, and it is the single strongest argument for UDP that exists.

The only integrity UDP offers

A checksum you are technically allowed to skip

Same ones’-complement algorithm as TCP, same pseudo-header — but with two twists that exist nowhere else in the stack.

The computation is identical to TCP’s: sum everything as 16-bit big-endian words with end-around carry, then complement. It covers three things:

  1. A 12-byte pseudo-header built from IP fields — source address, destination address, a zero byte, protocol number 17, and the UDP length. It is never transmitted; it exists so a datagram delivered to the wrong host fails validation.
  2. The 8-byte UDP header, with the checksum field itself set to zero.
  3. The payload, zero-padded to an even length if needed (the pad is not sent).

Twist one: zero means “I didn’t bother”

Over IPv4 the UDP checksum is optional. A sender that does not want to compute it transmits 0x0000, and the receiver skips verification entirely. This was a 1980 concession to slow hardware on trusted local links.

Over IPv6 it is mandatory, with no exceptions, because IPv6 removed the header checksum that IPv4 had. Take the checksum away at both layers and a single flipped bit in a destination address delivers your datagram to a stranger with nothing to catch it.

Twist two: the 0xFFFF substitution

Here is the detail that makes UDP’s checksum genuinely peculiar. What if the computed checksum legitimately comes out as 0x0000? It would be indistinguishable from “no checksum computed,” and every receiver would skip verification on exactly those datagrams.

RFC 768’s answer: transmit 0xFFFF instead. This works because in ones’-complement arithmetic there are two representations of zero — 0x0000 (positive zero) and 0xFFFF (negative zero) — and they are numerically equal. The receiver’s sum comes out the same either way. One value is reserved as a sentinel, the other carries the number.

Why it is worth knowing

It is the clearest example in networking of a spec exploiting a property of its arithmetic to smuggle a flag into a value field with zero cost. It also explains a real bug class: implementations that compute the checksum correctly but forget the substitution produce datagrams that some peers verify and others silently accept unchecked.

How big can a datagram be

65,507 bytes in theory. About 1,200 in practice.

The gap between those two numbers is where most real UDP bugs live.

The Length field is 16 bits and counts the header plus payload, so the ceiling is 65,535. But the IPv4 total length field is also 16 bits and has to hold the IP header too:

65,535   IPv4 total length, maximum
  − 20   IPv4 header
  −  8   UDP header
─────────
65,507   largest UDP payload over IPv4       (65,527 over IPv6; larger still with IPv6 jumbograms)

You should essentially never approach it. Anything larger than the path MTU minus 28 bytes gets fragmented by IP, and IP fragmentation is one of the most reliably disappointing mechanisms on the internet.

Fragmentation fails in more ways than plain loss. Many firewalls and load balancers drop non-initial fragments outright, because only the first fragment carries the UDP header — and therefore the port numbers a stateless filter needs to make a decision. NAT devices frequently mishandle them for the same reason.

Practical rule

Keep UDP payloads under about 1,200 bytes and you will fit inside essentially every path MTU on the internet, including tunnels and VPNs, without fragmenting. This is not folklore — it is what QUIC does (its minimum required datagram size is 1,200 bytes), what RFC 8085 advises, and what DNS resolvers converged on after fragmentation attacks. If your data does not fit, either implement your own splitting with per-piece recovery, or use TCP.

The DNS 512-byte rule, and how it was lifted

Classic DNS capped UDP responses at 512 bytes — chosen because RFC 791 guarantees every IPv4 host can reassemble at least 576 bytes, leaving room for headers. A response that did not fit set the TC (truncated) bit, and the resolver retried the whole query over TCP.

EDNS0 (RFC 6891) let a resolver advertise a larger buffer — often 4096 bytes — which worked until it did not: large fragmented responses became a fragmentation-attack vector and were dropped by middleboxes. Current practice has swung back hard. The DNS Flag Day 2020 consensus recommends advertising around 1232 bytes, small enough to never fragment, and falling back to TCP when a response exceeds it.

So DNS — the archetypal UDP protocol — ends up needing TCP as a companion. That is not a failure of UDP. It is UDP being used correctly: fast path over datagrams, reliable path for the rare large case.

No flow control, no congestion control

Nothing slows you down. That is your problem to solve.

TCP has two independent brakes — the receiver’s window and the sender’s congestion window. UDP has neither, and the failure is silent at both ends.

Overrun the receiver and its socket buffer fills. The kernel does not signal you, does not slow you down, and does not queue for later — it drops the datagram and increments a counter. The sending application sees a successful send(). The receiving application sees a gap it may not even know about.

$ netstat -su
Udp:
    481203 packets received
    1204 packet receive errors          ← datagrams dropped, for any reason
    1204 receive buffer errors          ← all of them: the socket buffer was full
    17 packets to unknown port received     ← these got an ICMP port-unreachable back

$ ss -ulnm 'sport = :5060'                # -m shows the socket memory
    skmem:(r0,rb212992,t0,tb212992,...)     ← rb = SO_RCVBUF, the drop threshold

The fix is a bigger buffer and a faster reader: raise SO_RCVBUF (bounded by net.core.rmem_max), and never do real work on the thread that calls recvfrom() — drain into a queue and process elsewhere. On high-rate receivers, recvmmsg() pulls many datagrams per syscall.

The part that affects everyone else

Overrun the network and there is no cwnd to collapse, no sawtooth, no backoff. A UDP sender in a tight loop will happily saturate a bottleneck link and keep going, and because loss-based TCP flows sharing that link do back off, your traffic crowds them out entirely.

RFC 8085 is not optional reading

The IETF’s UDP usage guidelines are blunt about this: an application sending more than a few datagrams per round trip should implement congestion control, no more aggressive than TCP would be under the same conditions. In IETF language that “should” means “do it unless you can defend not doing it” — a real engineering obligation, not etiquette — bulk UDP without backoff is how you cause an outage for traffic that has nothing to do with you. If you are sending at volume, use QUIC, or DCCP, or a rate limiter you actually tuned. “UDP is faster” stops being true the moment the bottleneck queue is full of your own retransmits.

A surprising API

You can call connect() on a UDP socket

It sends no packets and establishes nothing. It is still one of the most useful things you can do.

UDP is connectionless, so connect() looks like a category error. It is not — it is a purely local operation that stores a default peer in the socket, and it buys you three concrete things:

  1. You can use send() and recv() instead of sendto()/recvfrom(), without repeating the address on every call.
  2. The kernel filters inbound datagrams to that peer only. Datagrams from anyone else are not delivered to this socket. This is a convenience, not a security boundary — a source address can be forged.
  3. You start receiving ICMP errors. This is the big one.
The ICMP behaviour nobody expects

On an unconnected UDP socket, ICMP errors are discarded — the kernel has no way to know which of your many peers an error refers to, so sendto() to a host with nothing listening returns success and you learn nothing. On a connected UDP socket, that same ICMP port unreachable is matched to the socket and surfaces on your next call as ECONNREFUSED.

So the difference between “my UDP client hangs on a timeout forever” and “my UDP client fails instantly with a clear error” is one connect() call that transmits nothing.

It is also faster on Linux for repeated sends to the same destination, because the route lookup is cached on the socket rather than redone per datagram. To undo it, call connect() again with an address family of AF_UNSPEC.

Servers generally stay unconnected — one socket serving every client is UDP’s whole scaling advantage. Clients talking to one server should almost always connect.

The pattern

Read the last column and a rule emerges. These protocols did not choose UDP because they wanted less reliability — several of them rebuilt more machinery than TCP has. They chose it because they needed a different reliability: per-stream instead of per-connection, or bounded-latency instead of guaranteed, or none-at-all for data that expires faster than it can be repaired. TCP offers exactly one policy and it is not configurable. UDP offers none, so you can write your own.

One send, many receivers

Territory TCP cannot enter

TCP is definitionally point-to-point: a connection is a four-tuple between exactly two endpoints, and its acknowledgment mechanism has no meaning with a thousand receivers. UDP has no such constraint, so it owns everything one-to-many.

Unicast

One sender, one receiver. Both TCP and UDP. n receivers costs n copies on the wire.

Broadcast UDP only

To every host on the local link — 255.255.255.255 or the subnet broadcast. Routers do not forward it. This is how DHCP finds a server before it has an address. IPv6 removed broadcast entirely in favour of multicast.

Multicast UDP only

To a group address (224.0.0.0/4 in IPv4, ff00::/8 in IPv6) that receivers opt into via IGMP or MLD. The sender transmits one packet and the network duplicates it only where paths diverge.

Multicast is what lets an exchange fan a market-data feed out to hundreds of trading systems at identical latency from a single send, and what carries IPTV inside a provider’s network. Its limitation is reach: multicast is essentially undeliverable across the public internet, because it requires router support and inter-domain agreement that never materialised. Inside a datacenter or a carrier network it is indispensable; between them, nobody uses it.

Familiar group addresses you will meet: 224.0.0.1 all hosts on the subnet, 224.0.0.251 mDNS/Bonjour, 239.255.255.250 SSDP and UPnP device discovery.

The dark side

Why UDP is the internet’s favourite weapon

Two of UDP’s defining properties combine into the single most effective DDoS technique in existence. Understanding it is not optional if you deploy a UDP service.

The mechanism needs only two ingredients, and UDP supplies both:

  1. No handshake means the source address is never verified. TCP’s three-way handshake incidentally proves the client can receive at the address it claims — you cannot complete it while lying about who you are. UDP has no such step, so an attacker can put the victim’s address in the source field and the server will reply to the victim.
  2. Some UDP services answer a tiny question with an enormous reply. That ratio is the amplification factor, and the attacker’s bandwidth is multiplied by it.

What to do about it

If you operate a network: implement BCP 38 (RFC 2827) ingress filtering — drop outbound packets whose source address does not belong to your network. If every network did this, source spoofing would be impossible and this entire attack class would disappear. It has been the standing recommendation since 2000; adoption is still incomplete, which is why the attacks continue.

If you run a UDP service:

  • Never let the response be much larger than the request. This is the whole game. If your protocol can return a large reply to a small query, it is an amplifier.
  • Validate the source address before doing expensive work. This is exactly what QUIC’s address validation does: a server that has not yet confirmed a client’s address may not send more than three times what it received, and it can force a round trip with a Retry token — a handshake, reinvented precisely because UDP lacks one.
  • Rate-limit per source, and respond to repeated identical queries with a truncated answer that forces a TCP retry (this is DNS Response Rate Limiting).
  • Do not expose it by default. memcached, Redis, and SNMP have no business listening on a public interface. memcached disabled UDP by default in version 1.5.6, after the fact.
A test worth running

Point nmap -sU at your own public ranges. Every open UDP port that answers an unauthenticated query with a larger response is a weapon someone else can aim. It is the fastest security audit in networking and almost nobody does it.

Building on top

“We’ll just add reliability to UDP”

A reasonable instinct that has produced a great deal of broken software. Here is the actual bill.

The first six are a weekend. Congestion control is not. It took the networking community thirty years — from the congestion collapse of 1986, through Tahoe, Reno and CUBIC, to BBR in 2016 — to get it right. Getting it wrong does not produce a bug you notice in testing — it produces a system that works beautifully on your LAN and degrades the network for everyone once deployed.

The honest recommendation

If you need full reliability over UDP, use QUIC. It is RFC 9000, it is deployed at internet scale by Google, Cloudflare, Meta and Apple, it has been attacked and patched for years, and mature libraries exist for every language (quic-go, quinn, msquic, aioquic, lsquic). It gives you every row of that table plus TLS 1.3, multiple independent streams without head-of-line blocking, and connection migration across network changes.

Roll your own only when you genuinely need partial reliability — the case QUIC does not cover and TCP cannot express. Real-time media is the honest example: retransmit the keyframe, drop the stale audio packet, and never stall the stream for either.

The decision

Which one, and why

The useful question is not “do I need reliability?” — everyone says yes. It is “what is a late message worth to me?”

Ask it in this order:

  1. Is stale data worse than no data? If a message that arrives 300 ms late is useless or actively harmful — a video frame, a player’s position, a clock sample — retransmission is not a feature, it is damage. UDP.
  2. Does one lost message have to block the others? If you have independent streams sharing a link, TCP will stall all of them for one loss. QUIC over UDP.
  3. Is it one small request and one small reply? A handshake would dominate the cost. UDP, with your own timeout and retry.
  4. Do you need one-to-many? UDP. TCP cannot do it at all.
  5. Is there no IP address yet, or no network state to rely on? UDP.
  6. Anything else — a bulk transfer, an API call, a database connection? TCP. Use the thirty years of tuning that already exist.
Two myths worth dropping

“UDP is faster than TCP.” Not in throughput — on a healthy path a single TCP flow will beat naive UDP, because congestion control keeps it out of full queues. UDP wins on latency: no setup round trip, and no head-of-line blocking. Those are different words and the difference matters.

“UDP is unreliable, so it’s for unimportant data.” UDP carries DNS, the boot process of every device on a network, the world’s time synchronisation, and a large and rising share of all web traffic via HTTP/3. It is not the protocol for data that does not matter. It is the protocol for data whose value decays faster than the network can repair it — or whose recovery you want to control yourself.

Reference card

The numbers worth memorising

Header

8 bytes, always. Source port, destination port, length, checksum — 16 bits each. No options, no flags, no sequence number.

Sizes

Max payload 65,507 B over IPv4 (65,527 over IPv6). Stay under ~1,200 B to never fragment. Length field counts header + payload, minimum 8.

Checksum

Optional on IPv4 (0x0000 = not computed), mandatory on IPv6. A real zero result is sent as 0xFFFF. Covers a 12-byte pseudo-header, protocol number 17.

Guarantees

Kept: message boundaries, all-or-nothing delivery, integrity if the checksum is on. Absent: delivery, ordering, duplicate suppression, flow control, congestion control.
